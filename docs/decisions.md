# Decisions

## 2026-11-19 — clj-replace regression tests as data-driven black-box cases

Before: clj-replace had only `evals/evals.json`, which checks whether an LLM chooses the skill, not whether `scripts/clj-replace.bb` matches correctly. Issue #3 (`#()` never matches) showed the script itself had no tests.
Decision: Add `skills/clj-replace/test/` beside `scripts/` (not inside it, so the agent does not see fixtures among the tools it runs): `cases.edn` holds one map per case (file, old, new, expected exit and file), and `run.bb` runs the script as a subprocess for each case. Cases for bugs not fixed yet carry `:known-bug true` and count as expected failures; one that passes fails the run (XPASS). A root `bb.edn` adds `bb test`. `CLJ_REPLACE_SCRIPT` points the runner at another implementation.
Reason: Issue #3 offers two fixes (normalise gensyms vs compare rewrite-clj nodes) and probing found ten more cases of the same root cause, `(= (z/sexpr a) (z/sexpr b))` not meaning "same source": false negatives (`##NaN`, `#()` in syntax-quote) and silent false positives (metadata, `#_`, vector vs list, `1` vs `1N`). Black-box cases let both fixes run against one suite: the gensym-normalising prototype turns 4 of the 11 known bugs into XPASS and leaves 7.

## 2026-11-19 — clj-replace exit 4: text present but no structural match

Superseded by: 2026-11-19 — clj-replace exit 4 becomes a near match that shows the file's text

Before: When the structural comparison found nothing, clj-replace always printed "No matching S-expression found" (exit 2). For forms containing `#()` that reads as a typo in old-string although the text is in the file verbatim (issue #3, "distinguish the two failures"). The issue suggests detecting `#()` in old-string.
Decision: On no structural match, look for nodes whose source text equals old-string up to whitespace. If any exist, exit 4 with their locations, saying this is a clj-replace limitation and to use a plain text edit; otherwise exit 2 as before. Only the diagnosis changes; no edit is made on either path.
Reason: Detecting `#()` covers one cause; probing found at least six false negatives with different causes (`#()`, `%&`, `#()` in syntax-quote, `##NaN`), and comparing text covers them all, including ones not found yet. Comparing node text (not a raw substring search) keeps text inside comments or string literals out (`text-only-in-comment`, `text-only-in-string` cases stay exit 2). A separate exit code lets an agent switch to a text edit, which is guaranteed to find the text, instead of rewriting old-string. It does not address silent false positives (metadata, `#_`, vector vs list, `1` vs `1N`); those need the comparison itself to change. The known-bug cases now pin today's behaviour with `:interim`, so the runner notices when a bug's behaviour changes.

## 2026-11-19 — clj-replace: a different spelling of the same value is no match

Before: clj-replace compares `z/sexpr` with `=`, so code that reads to the same value matches whatever its spelling: `{:a 1 :b 2}` and `{:b 2 :a 1}`, `'x` and `(quote x)`, `#'a` and `(var a)`, `0xFF` and `255`, `1.0` and `1.00`, a string with `\n` and one with a literal line break, and a form with or without an inner `;` comment (replacing then deletes the comment). Yet `@a` does not match `(deref a)`.
Decision: clj-replace ignores layout only: whitespace, commas and line breaks between tokens. Any other difference in source, including map and set order, reader-macro versus long form, number spelling and comments, is no match. Recorded as known-bug cases in `skills/clj-replace/test/cases.edn` (`:expect {:exit 2}`, `:interim` pinning today's exit 0).
Reason: The skill promises a replacement that ignores formatting, not one that ignores spelling. Matching a different spelling replaces code the user did not write in old-string, and for inner comments it silently loses text. The equal-value cases were found by mining eastwood and splint (`resource/var-info.edn:756`, `linters/typos.clj:932`, `pattern_test.clj:33`, `priority_map.clj:353`).

## 2026-11-19 — clj-replace exit 4 becomes a near match that shows the file's text

Before: Exit 4 meant "old-string, with whitespace collapsed, appears in the file but the structural comparison missed it". The previous entry made every different spelling of the same value no match (exit 2), and re-examining it showed two kinds of difference: ones that lose information the agent did not see (inner comments, metadata, type hints, `#_`), and pure spelling (map or set order, `'x` vs `(quote x)`, `#'a` vs `(var a)`, `0xFF` vs `255`, `1.0` vs `1.00`, string escapes). A plain exit 2 leaves the agent guessing why its old-string failed. The collapsed-whitespace check also misreports `(f "a b")` against `(f "a  b")` as a tool limitation although the string contents differ.
Decision: Keep "different spelling is no match" for both kinds. When no node matches up to layout but some node has the same value (today's `z/sexpr` + `=` comparison), exit 4 and print each such node's location and its exact text from the file, so the agent retries with that text. Otherwise exit 2. The collapsed-whitespace text check is dropped. Recorded in `skills/clj-replace/test/cases.edn`: 17 false-positive cases now expect exit 4 with the file's text in the output, and `string-inner-whitespace` expects exit 2.
Reason: Matching only up to layout keeps one rule that is easy to predict and needs no value normalisation in the new comparison. Showing the file's text makes the rule cheap to follow: one retry, and the agent sees the comment or metadata it would otherwise have deleted. Discussed and chosen with the user after weighing "match pure spelling differences" (one-shot success, but needs order-insensitive maps, quote and number normalisation) against this.

## 2026-11-19 — clj-replace: one form in, comments are content

Before: clj-replace read only the first form of old-string and of new-string, so `"(a) (c)"` matched `(a)` and ignored `(c)`, `"(x) (y)"` wrote only `(x)`, and a top-level comment in new-string was dropped while the success message printed it. Comments inside a form were invisible to the comparison.
Decision: old-string must hold exactly one form, with no top-level comment; otherwise exit 1 saying so. new-string must hold exactly one form, or be blank, which deletes the matched form (as today); anything else is exit 1. Several forms in new-string may become a feature later, under its own cases. Comments inside a form are content: they must have the same text in the same place, except trailing whitespace at the end of a comment line; a difference gives the exit 4 near match with the file's text. Recorded as cases in `skills/clj-replace/test/cases.edn` (groups `:input`, `:basic`, `:false-positive`).
Reason: Each of these silently dropped text the caller wrote. Rejecting several forms keeps this change a fix rather than a new range-replace feature. Blank new-string already deletes and callers may rely on it, so it stays. Comment equality is cheap to follow because exit 4 shows the file's text, and a single rule (only trailing whitespace is ignored) is easier to predict than more exceptions. Agreed with the user.

## 2026-11-19 — clj-replace compares canonical node text instead of sexpr

Superseded by: 2026-11-19 — clj-replace compares node trees with early exit; corrected performance

Before: `walk-and-find` matched a node when `(= (z/sexpr node) (z/sexpr old))`. Issue #3 proposed normalising the gensyms of `#()` (option 1, binding `*gensym-counter*`, is not possible: the var does not exist) or comparing nodes. Mining eastwood and splint showed sexpr discards what the earlier decisions require to be compared (map order, `'x` vs `(quote x)`, number spelling, comments, `#_`), so no patch of the sexpr comparison can meet them.
Decision: Compare a canonical rendering of each rewrite-clj node: layout nodes (whitespace, newline, comma) are dropped and one space separates the remaining children, leaves keep their source text, and comments keep their text minus trailing whitespace and end with a newline. One pass over the file collects exact matches and, for the exit 4 near match, nodes whose `n/sexpr` equals old-string's (guarded, so `#_` cannot crash). Inputs are parsed with `parse-string-all` to enforce one form.
Reason: Of the options compared (gensym normalisation: fixes 4 of the 37 known-bug cases; patching sexpr equality: about 15, the rest impossible; regex over source: needs its own lexer), only node comparison matches "ignore layout only". The prototype turned all 37 known-bug cases into passes with no regression (77 cases), passed the corpus property test on 2,600 sampled forms from eastwood and splint (0 failures; the old script failed on #() and #_ forms), and is faster on the no-match path because it walks once: 199 ms vs 249 ms on a 2,183-line file, 813 ms vs 1,071 ms on 10,915 lines (hyperfine, median).

## 2026-11-19 — clj-replace compares node trees with early exit; corrected performance

Before: The previous entry rendered a canonical string for every node and claimed the new script was faster (199 ms vs 249 ms on a 2,183-line file). Code review found the baseline was wrong: those 249 ms were the intermediate script with the exit-4 text check, not the released 1.0.0 script. Against 1.0.0 the committed script was 27% slower on that file, 1.6x on a 12,000-line file and 4.3x on 20 forms nested 300 deep, because rendering every node's subtree costs nodes x depth, and the value comparison ran on every node even when an exact match existed.
Decision: Same matching rule, different implementation. `same-source?` compares two node trees directly: tag, number of non-layout children, delimiters (the node's text without children), then children in order; leaves compare source text, comments up to trailing whitespace; it stops at the first difference. The walk is one pass, collects no node list, and compares values for the exit 4 near match only until the first exact match. Gensyms are renamed for the near match only when old-string's value has one.
Reason: hyperfine medians (9 runs), 1.0.0 script vs this one: tiny file 30 vs 32 ms; 2,183 lines (no match) 151 vs 154 ms; 10,915 lines 610 vs 623 ms; 12,000 lines 851 vs 895 ms; deeply nested 341 vs 344 ms; matching the last form of the 2,183-line file 161 vs 165 ms. Profiling the 12,000-line file showed the remaining cost is the position-tracking zipper walk (about 280-350 ms) that both versions do; collecting the node list had cost about 140 ms and a lazy `for` about 120 ms, both removed. `bb test` 80/80, corpus property test 0 failures on 1,000 sampled forms (eastwood and splint).
